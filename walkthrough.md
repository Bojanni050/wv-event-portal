## 2026-10-07 (PostgreSQL refactor — Phase 1: data layer)

- Findings: The backend was fully coupled to MongoDB via Motor/GridFS (`core.py` connection + `BaseDocument.from_mongo/to_mongo`, `oid()`/`PyObjectId`, `$set`/`$in`/`$group` query filters, GridFS for file bytes, and `create_index` in `seed.py`). No `.env` existed and the app could not run locally (Motor missing); a local PostgreSQL 18 service was available on :5432, so it was used instead of the bundled Docker compose (Docker daemon was down).
- Conclusions: Chose SQLAlchemy 2.0 async ORM + asyncpg with UUID primary keys, Alembic migrations, and `BYTEA` for file contents (all confirmed with the user). Kept the JSON API byte-compatible so the React app needs no changes. A field named `date` collided with `datetime.date` when Pydantic resolved annotations in the class namespace (`Optional[date]` became `Optional[None]`); fixed by importing the module as `dt`. Raw string dates cannot be passed straight into ORM `Date` columns — anything building ORM rows directly (seed/integrations) must pass `date` objects; request schemas already parse strings.

Routes/auth/seed/tests still use the old Mongo layer and will be ported in Phases 2–6.

## 2026-10-07 (PostgreSQL refactor — Phases 2–6: full backend cutover)

- Findings: Porting revealed two behavioural traps that would have silently broken the app: (1) a field literally named `date` shadows the `datetime.date` type during Pydantic annotation resolution, turning `Optional[date]` into `Optional[None]` — fixed by importing the module as `dt`; (2) `rsvp_deadline` was a free-text string in the original (`"15 mei 2027"`) and is displayed as such, so it could not become a `Date` column. Directly-built ORM rows (seed/integrations) also cannot take raw date strings. Direct-DB test helpers that call `asyncio.run()` per operation must not use a pooled async engine, because asyncpg connections bind to the loop that created them.
- Conclusions: Kept the JSON API contract byte-compatible (string UUIDs, `date` as `"YYYY-MM-DD"`, unchanged field names) so the frontend needs no changes. Preserved original semantics exactly: `event_scope`/`unread_filter` became SQLAlchemy conditions, `services.event_stats` runs `GROUP BY` instead of `$group`, event children rely on real FK `ON DELETE CASCADE`, and file bytes live in `BYTEA`. The test suite mutates one shared seeded dataset (sanne's password, jeroen's single event) across modules/classes, so it is only reliable serially (`-n 0`); `--dist loadscope` splits those classes across workers and races on shared rows — a pre-existing design issue, not a port defect.
- Actions: Rewrote `core.py` (UUID auth/scoping), `services.py`, `seed.py`, `server.py` (engine dispose) and all 11 route modules against SQLAlchemy sessions; `schemas.py` gained request/response models and `tests/helpers.py` was added with a `NullPool` engine and sync wrappers. Ported all four DB-touching suites (`test_welcome`, `test_password_reset`, `test_account`, `test_rsvp`) plus `backend_test.py` to env-driven credentials and Postgres helpers. Validated end to end: an app import check; a 40-assertion HTTP smoke test (auth, scoping/RBAC, events, chat, music, timeline, bytea file round-trip, invitation + public RSVP, WordPress upsert, cascade delete) all green; and the pytest suite green serially twice (`69 passed, 1 skipped` — the skip is the welcome email blocked locally because `FRONTEND_URL` is `http://` while the mailer requires https links). Observations flagged, not changed: the mailer's credential scanner also scans the reset token, so a random token containing e.g. `cvv` can false-positive; and the JWT dev secret was lengthened to avoid `InsecureKeyLengthWarning`.

## 2026-10-07 (Deploy hardening)

- Findings: Startup unconditionally ran `seed_demo()` (real demo customers/events on a first production boot) and read `os.environ["DEMO_PASSWORD"]` *before* the "events exist?" guard, so production would crash without that dev-only secret. `ensure_user()` overwrote the admin password whenever it differed from `ADMIN_PASSWORD`, silently reverting any in-app password change on restart. The frontend read `REACT_APP_BACKEND_URL` with no default and had no `.env.example`, so a build without it yields `undefined/api`. There was no migration step for deploy, and `password_reset_tokens`/`login_attempts` grew unbounded (the old Mongo schema had a TTL index on the former).
- Conclusions: Demo data must be opt-in (`SEED_DEMO`, default false) with `DEMO_PASSWORD` read only inside that branch; admin provisioning should be create-only; stale rows need pruning at startup, which required a timestamp on `login_attempts`. Kept the app functional in dev by setting `SEED_DEMO=true` in the local `.env`. Production values (`CORS_ORIGINS`, `FRONTEND_URL`) must be the https domain, and `FRONTEND_URL` must be https or the email link guard rejects reset/welcome mail.
- Actions: Reworked `backend/seed.py` (`_demo_seed_enabled`, `ensure_templates`, `cleanup_expired`, create-only `ensure_user`, gated `seed_demo`); added `login_attempts.updated_at` to `backend/models.py` with migration `fa25cd274bc8_add_login_attempts_updated_at.py`; rewrote `backend/.env.example` and `backend/.env` (added `SEED_DEMO`, prod-oriented comments, TLS note); added `frontend/.env.example` and `backend/entrypoint.sh` (`alembic upgrade head` + uvicorn); replaced the stub `README.md` with setup/env/deploy docs; updated the stale MongoDB references in `memory/PRD.md`; added a `.gitignore` exception for `frontend/.env.example`. Validated on a fresh schema: `SEED_DEMO=false` seeds only admin + 5 templates (no demo); the admin password survives a restart; `SEED_DEMO=true` restores full demo data; `cleanup_expired` deletes an expired reset token and a stale login attempt; the pytest suite stayed green serially (`69 passed, 1 skipped`).
